1.3 「生态适配数量」的口径陷阱〔本节 B/C 级数字年份多未披露，一律视为待核实〕

行业稿件常见表述：「适配软件超 400 万款」「生态兼容超 1000 万件」「累计部署超 2000 万套」「装机超 5000 万台」「openEuler 累计装机超 610 万套 / 1600 万套」〔C，多为厂商宣传或聚合稿，同一指标在不同稿件中数值差异达 2—3 倍〕。

必须区分四个不同指标：

  1. 适配条目数（软硬件组合/版本配对计数）——一次软件与一个 OS 版本 + 一个 CPU 架构的组合即可能计为一条，天然远大于独立软件数。
  2. 独立软件/硬件型号数——去重后的产品数。
  3. 部署套数 / 装机量——含测试环境、预装、历史累计，不等同活跃付费用户。
  4. 生态伙伴数——注册厂商数，与适配深度无关。

使用建议：招标中不要以「适配 XX 万款」作为技术评分依据，应要求供应商提供本项目涉及的软件清单在指定 CPU + OS + 内核版本组合下的适配证明与压测报告。

1.4 CentOS 停服与迁移工具

CentOS 停服构成国产 OS 替代的重要窗口。厂商侧已形成相对成熟的迁移工具链：桌面环境克隆式搬迁、Windows 驱动迁移（deepin-wine 类技术）、AD 域与组策略替代（集中域管平台）、自动化迁移与回退脚本。公开案例包括单台服务器迁移控制在 30 分钟内、某省医保局 5000 余套 CentOS 服务器 4 个月完成迁移〔C，厂商/行业稿，属案例宣传，需以项目验收材料核实〕。

工程判断：迁移工具能降低重复劳动，但不能替代兼容性预检与业务回归。真正决定工期的是外设驱动、字体渲染、打印控件与 ActiveX 类组件，详见 07。

2.3 选型维度（按重要性排序）

  1. SQL 方言与存量资产：分页语法、序列/自增、隐式类型转换、CONNECT BY 递归、PL/SQL 包体、DBMS_LOB、触发器、存储过程、执行计划与索引策略。
  2. 迁移工具链成熟度：是否支持结构转换、全量+增量同步、DDL 同步、字段级比对、校验与回滚。有案例显示 DDL 同步能力是异构迁移的「隐形守护者」〔C，厂商技术博客〕。
  3. 高可用与容灾：RPO / RTO、同城双活、异地灾备、故障切换演练记录。
  4. 性能特征：OLTP / OLAP / HTAP 负载匹配、批量与跑批窗口、连接池行为。
  5. 生态与运维：监控、备份、审计、SQL 审核工具、DBA 人才可得性。
  6. 合规资质：安全可靠测评等级、等保与密评支撑能力、国密算法支持。
  7. 商业可持续性：厂商交付能力、版本路线、维保成本、是否有同类核心系统案例。

4. 云平台：一云多芯是碎片化的主要收敛手段

4.1 能力模型

层能力作用
硬件抽象层算力插件 / 算力网关，将 x86、ARM、LoongArch、RISC-V 抽象为统一逻辑资源池屏蔽芯片差异
平台服务层跨架构虚拟化规范、虚拟机/容器镜像可迁移、统一调度与 NUMA 感知降低运维复杂度
应用开发层标准 API、多架构构建与镜像分发开发者无需感知底层架构
多云管理（CMP）统一纳管信创私有云、传统虚拟化、公有云存量资产盘活、成本可视化

4.2 实践要点

  • 混合部署是常态而非过渡态：多批次采购必然形成 x86 与国产 CPU 并存，一云多芯的价值在于把「多架构」从应用侧问题收敛为平台侧问题。公开方案显示可同时调度飞腾、鲲鹏、海光等异构 CPU，并兼容异构存储与网络设备〔B/C，中国电子云 CECSTACK 白皮书、EasyStack ECF 资料〕。
  • 镜像必须多架构：容器镜像按 linux/amd64 / linux/arm64 / linux/loong64 分别构建并使用 manifest list（loong64 为容器平台标识，loongarch64 仅为 uname -m 输出），基础镜像需含对应架构的 JDK 与 native 依赖。
  • NUMA 与调度：国产多核平台存在 NUMA 架构下的性能衰减问题，需在内核调度、内存管理、中断处理层面做针对性优化〔C，厂商技术文章〕。
  • 存量利用：老型号服务器在健康达标（NVMe/S.M.A.R.T. 检测）前提下可纳入统一资源池，降低 TCO。
  • 风险：平台层屏蔽差异的同时也带来厂商锁定；应在合同中约定镜像可导出、API 兼容与数据可迁移条款。

4.3 存储与网络

  • 软件定义存储（SDS）已成信创云数据基石，支持块/文件/对象三种接口，完成与主流国产 CPU/OS 的适配及百余家厂商互认证〔C，厂商资料〕。
  • 网络设备（核心/汇聚/接入交换机、路由器、网卡）国产化率相对较高，但高端射频、光模块、SR-IOV/RDMA 支持需在选型时实测。

资源与部署YARN / Kubernetes、对象存储 / HDFS一云多芯下的混合调度、NUMA 亲和、国产对象存储 S3 兼容度
安全治理Ranger / Kerberos / LDAP、审计与脱敏国密改造（TLCP/SM4）、密评边界、账号体系与信创目录服务对接

国产供给以「开源根社区 + 商业发行版/托管服务」为主：Hadoop/Spark/Flink/Iceberg 等上游多为国际开源社区，国内厂商提供发行版、运维平台与适配认证；Doris、Paimon、Kylin 等项目国内贡献度较高〔B/C，社区与厂商公开资料，具体份额待核实〕。因此这一层的「国产化」更多体现为发行版可控、适配认证与运维能力，而非「内核全部自研」——与 09 §4 对开源依赖的判断一致。

5.2 适配与迁移要点

  1. 先分清「计算迁移」与「数据迁移」：列式文件（Parquet/ORC）与湖表元数据一般跨 CPU 架构可读，真正要重做的是计算引擎二进制、JNI 压缩库（snappy/lz4/zstd）、JDK 与 glibc 组合。据此可显著缩小 S3 阶段的数据搬迁量。
  2. native 依赖是头号阻塞点：RocksDB、LevelDB、OpenSSL、netty-transport-native-epoll、SIMD 加速路径需逐架构编译并做指令集回退验证；纯 Java/Scala 作业通常可直接跨架构运行。
  3. SQL 方言比 CPU 更贵：Hive/Spark/Presto 与国产 MPP 引擎在窗口函数、隐式类型转换、分区语法、时间戳精度上不一致，须按 07 §5.4 的方言清单逐条回归。
  4. 权限与审计不可丢：迁移常重建 Ranger/LDAP 而遗漏行列级策略、脱敏规则与审计留痕，属等保/密评检查高发项，见 06 §7。
  5. 双跑比对口径：按「任务级输出行数 + 主键集合 + 关键指标哈希」三重比对，而非只比对作业成功状态；历史分区抽样回算，避免统计口径漂移。
  6. 阶段归属：平台盘点与 native 依赖确认属 S0，引擎冒烟与 SQL 回归属 S1/S2，元数据/权限/历史数据迁移与双跑属 S3，全站阶段定义以 07 §3 的 S0—S5 为唯一主表。

口径提示：本节厂商与份额类描述多为 B/C 级转引、缺少统一统计时点，按 README §四规则一律视为「待核实」，不得单独作为选型或招标依据。

均为 OpenJDK 衍生发行版，覆盖 Java 8/11/17/21 LTS〔B/C，厂商与行业资料〕。版本矩阵是真实风险：数据库 JDBC 驱动对高版本 JDK 的支持往往滞后，早期 DM8 驱动在 JDK 17+ 上出现模块化反射限制问题〔C，技术博客〕。选型时应以实际驱动版本 + 目标 JDK 版本组合做压测，而不是采信文档中的「支持」。

7.2 编译器、IDE 与 CI/CD

  • 编译器：毕昇编译器、GCC/LLVM 的国产架构后端、龙芯工具链。
  • IDE 与构建：主流 IDE 在国产 OS 上可用；需配置国产 Maven/Gradle 镜像、多架构 CI 构建节点。
  • 运维：容器平台（KubeSphere 等）、监控、日志、APM 需确认目标架构 Agent 可用——监控/APM Agent 常是迁移中最容易被遗漏的闭源二进制依赖。

9. 本章小结

  • 操作系统已形成「双寡头 + 云厂商 OS + 开源根社区」结构，内核向 6.6 收敛；适配结论不可跨内核版本沿用。
  • 「适配千万款」「装机千万套」类数字口径混乱，招标应改为「本项目软件清单 × 指定组合」的适配证明。
  • 2026 年第 2 号公告给出 8 款集中式 + 15 款分布式数据库测评结果，其中 Ⅱ 级 5 款；选型必须核对产品名、版本号、公告批次与三年有效期。
  • 中间件是 Java 栈最直接替换点，但纯 Java/开源组件应优先保留，把预算集中在合规点名的层。
  • 一云多芯是碎片化的主要收敛手段，同时带来平台锁定风险；多架构镜像与 NUMA 调优是落地关键。
  • 大数据平台与数据湖属 L4 平台软件，国产化主要体现为发行版可控与适配能力；数据本体多可跨架构保留，风险集中在 native 依赖、SQL 方言、元数据与权限（§5）。
  • 国产 JDK 均为 OpenJDK 衍生，驱动版本 × JDK 版本 × CPU 架构的组合压测不可省略，详见 07 的 Java 专项。
